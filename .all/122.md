# Reduce Git subprocesses during board saves

## Initial proposal

Blob writes go through gitdb now, but each save still spawns a handful of
subprocesses: one mktree per column + .all + root, commit-tree, update-ref,
and merges shell out to merge-tree. GitPython/gitdb can build tree and commit
objects in-process too, and `merge-tree -z` gives structured conflict output
if we keep it.

Zero-subprocess saves; only worth doing if save latency matters again after
the 10x from in-process blobs.

## Resolution

Implemented in code commit 5906a7d. Reducing process churn is worthwhile independently of save latency.

Blobs, trees, and standard commits use GitPython/gitdb in-process with the pure GitDB backend. Object and ref reads no longer launch Git, and conflict path updates rebuild affected trees directly without temporary indexes.

Process-count regressions observe actual subprocess launches: an unchanged save launches none, a standard changed save launches only git update-ref, and a changed save with Git configuration environment overrides uses commit-tree plus update-ref. Linked worktrees also retain commit-tree to preserve their configuration semantics. Counts do not grow with column count. Git still handles compare-and-swap, merge-tree, merge-base, and history queries for ID-collision attribution.

Validation: regression confirmed the old unchanged one-column save launched five Git commands. Added Git object hash comparisons, dates and identities, packed objects/refs, bare and linked-worktree saves, unchanged index/worktree checks, git fsck, and two competing writer processes. Final full suite: 765 passed. Commit hooks passed.
