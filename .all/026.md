# conflict on new card

Concurrent card creation allocates the same id on multiple replicas
(`next_id` has no coordination); the file-level merge then collapses the two
cards into one — one side's content is lost and the column links double up.

## Agreed design (2026-08-07)

- **Detect**: add/add conflicts on `.all/<id>.md` (path absent from the merge
  base, added with different content on both sides) are id collisions, not
  edit conflicts. Precise signal, no heuristics.
- **Decide**: the card that entered history first keeps the id — first-added
  committer timestamp on each side (`git log --diff-filter=A`), tiebreak on
  commit sha. Computed from shared history, so every replica converges on the
  same answer regardless of merge direction.
- **Renumber**: the newer card moves to the next free id (mapping table for
  multi-collision merges).
- **Rewrite** on the renumbered side only, attributed via base/ours/theirs
  blob comparison:
  - symlinks: retargeted (guaranteed)
  - `deps` front-matter entries: remapped (guaranteed, structured)
  - `#<id>` tokens in card text: remapped — these are real references (the UI
    renders them as links). Bare numbers without `#` are prose and are never
    touched.

## Live reproduction 2026-08-07

TUI and CLI both created a card concurrently; both replicas allocated next id
124. `.all/124.md` resolved most-recent-wins (the TUI's card won, the CLI's
body was lost) and both column links survived, so 124 appeared twice in
Backlog. Repaired by hand in ganban commit 8a9a02e; the lost card was
recreated as 125.
